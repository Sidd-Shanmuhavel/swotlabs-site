# GK Policy Chatbot (Greene Genie) — Conversational Policy Assistant

## Part One — Business Overview (for all readers)

This assistant answers policy questions for staff at a UK pub and brewing company. Ask in plain English and it replies from the company's own policies, user guides and operational documents, with citations. Pub managers and kitchen managers use it most. They run daily operations and need the company line on something without working through a corporate document library to find it.

Any large organisation has this problem. The information sits across hundreds of documents in SharePoint, and getting an answer means knowing which document holds it and where to look inside. An employee types the question instead. The assistant searches the policy library, finds the passages that bear on the question, and writes an answer with citations back to the source documents, so the reader can check it against the policy.

The assistant answers from Greene King's documents and nothing else. It cites what it used. When it finds no relevant passage it says so instead of guessing, which is the behaviour that makes it safe to act on. It handles greetings, thanks and follow-up questions without losing the thread of a policy question.

Staff reach company knowledge faster and act on the current policy rather than a half-remembered one. The pipeline syncs new and changed documents from SharePoint each day, and every candidate version has to pass an evaluation of its answers before it reaches production.

## Part Two — How It Works End to End (for semi-technical readers)

The assistant uses retrieval-augmented generation (RAG). Rather than ask a model to answer from memory, you retrieve the source material first and then ask the model to answer from that material alone. The retrieval step is what makes an answer grounded and citable.

The system has two halves: a document pipeline that prepares the knowledge, and an agent that answers questions.

The **document pipeline** runs once a day. It connects to Greene King's SharePoint, finds the documents that are new or changed, and copies them into Azure storage. It extracts the text from each PDF and Word file and splits it into chunks, coherent passages of a few hundred words. A model does the splitting, and it also titles each chunk and writes out the questions that chunk could answer, which sharpens the search later. The pipeline cleans and quality-checks the chunks, embeds them, and loads them into a vector index, a database that finds passages by meaning rather than by keyword.

The **agent** is the part employees talk to. It reads the intent of an incoming message first, separating a greeting or a thank-you from a policy question. For a question it rewrites the text to stand on its own, resolving references like "what about that?", and searches the vector index. A model then grades each retrieved chunk for relevance and drops the ones that miss. The agent writes its answer from the chunks that survive, inserts the citation markers, and returns the sources with it.

The agent runs as a live service on Databricks behind a web interface. Each new version faces a test set of generated questions and reaches production only if it passes, a champion-versus-challenger promotion. Configuration is per environment, and Azure DevOps handles the deployment.

## Part Three — Deep Technical Reference (for engineers)

### Architecture and document flow

The end-to-end flow is SharePoint to Azure Blob Storage to a Databricks Vector Search index to a LangGraph agent to the user. The pipeline divides into ingestion (a sync service retrieves documents from a SharePoint corporate library), processing (documents are extracted, semantically chunked, and embedded), retrieval (the vector index enables semantic matching), generation (the agent retrieves chunks and produces cited answers), and serving (the agent runs as a Databricks serving endpoint behind a conversational UI app).

### The agent (`agent/agent/`)

`langgraph_chat_agent.py` is an MLflow `ResponsesAgent` wrapper implementing `predict()` and `predict_stream()`, converting a `ResponsesAgentRequest` into LangChain messages, streaming the graph, and extracting sources and trace identifiers into a `ResponsesAgentResponse`. `define_agent_graph.py` compiles the LangGraph `StateGraph` with its nodes and conditional edges, defining routing through `decide_route`, `decide_to_retrieve`, and `decide_to_generate`.

`nodes.py` implements the node logic: `detect_intent()` uses ChatDatabricks with structured output to classify input into greeting_hello, greeting_goodbye, specific_question, metadata_query, or thanks; `rephrase_question()` clarifies ambiguous questions from conversation history or detects a "no_question" state; `retrieve_chunks()` calls the retriever for the top-k documents; `generate_answer()` produces a cited response via the `Answer` structured output; `handle_non_queries()` responds to greetings and thanks; and `no_question()`, `no_answer()`, `start_conversation()`, `end_conversation()`, and `welcome()` handle lifecycle and fallback cases.

`retriever.py` integrates Databricks `VectorSearchClient`, performing a `similarity_search()` returning metadata (id, content, chunk_title, file_name, url, document_title), then calling `parallel_grade_documents()` to filter by relevance, returning LangChain `Document` objects. `grade_documents.py` performs that filtering with a `ThreadPoolExecutor`, grading each document against the query with a binary yes/no score, preserving OpenTelemetry span context for tracing.

`prompts.py` defines five templates: `prompt_generate_answer` (answer from sources with `<cite N>` tags, returning JSON of answer plus references), `prompt_grade_single_document` (binary relevance), `prompt_detect_intent`, `prompt_rephrase_question`, and `evaluation_questions_guidelines` (persona-based examples for evaluation generation). `models.py` holds the data models: `IntentEnum`, `Intent`, the LangGraph `State` TypedDict (messages with the `add_messages` reducer, question, sources, intent), `GradeDocuments`, `Reference` (citation number, chunk title, document title), `Answer`, and `AgentConfigSchema` (LLM endpoint dictionary, top_k, index details, temperature, max_tokens, request_timeout). `agent_config.py` carries static metadata (bot_name "Greene Genie", company_name "Greene King", mission and company description). `utils.py` provides `convert_to_documents()`, `convert_documents_to_dict()`, `get_context_formatted()`, `remove_cite_tags()`, `update_mlflow_trace()` (annotating traces with user, session, and conversation identifiers), and `get_dependencies_from_pyproject()`.

The default model is gpt-4o-mini, configurable per node through the LLM endpoint dictionary, served via ChatDatabricks, at temperature 0.0, max_tokens 1000, and a 20-second request timeout. The graph topology routes from START through `detect_intent`: greetings and thanks go to `handle_non_queries` then END; metadata queries go to a metadata handler then END; specific questions go to `rephrase_question`, then either to `no_question` and END, or onward to the retriever, then either to `no_answer` and END (when no sources survive) or to the generator and END.

### The sync service (`sync/sync/`)

The SharePoint client (`sharepoint_client/`) authenticates via MSAL `ConfidentialClientApplication` using service-principal credentials and the Microsoft Graph API; `client.py` exposes `iter_items()` to recursively traverse drive folders and `download_file()` to fetch content; `config.py` validates a `SharePointConfig` (client id and secret, tenant, domain, site path, and an environment-specific folder id such as GenAIDevInt5Yr, GenAITestInt5Yr, or GenAIProdInt5Yr); supporting modules are `types.py`, `functions.py`, and `errors.py`.

The blob storage client (`storage_clients/`) authenticates via Azure `ClientSecretCredential` and `BlobServiceClient`; `blob_client.py` exposes upload, delete, download, and list; `config.py` validates a `BlobConfig` (client id, secret, tenant, storage account, container name); `base_storage.py` is the abstract base.

The sync service (`sync_service/`) coordinates the workflow: `sync.py` (`SharePointSyncService`, tracking create/update/delete/relocate operations into an activity log and exposing `_log_operation()`, `_upload_to_blob()`, and `sync()`); `state_manager.py` (`StateManager` with an immutable `FileState` dataclass, comparing current SharePoint state against a previous JSON snapshot stored in blob to determine `_to_create`, `_to_update`, `_to_relocate`, and `_to_delete` lists); `extract.py` (the semantic chunking engine whose `chunk_text()` calls a ChatDatabricks endpoint with a prompt instructing 500–1000-word semantic chunks, each with a chunk title and up to a configured number of questions, plus a document title and a roughly 100-word summary, using tiktoken for token counts); `text.py` (`get_text_from_pdf()` via pypdf, `get_text_from_docx()` via python-docx, and `get_text_from_blob()` routing by magic-byte format detection); and `schemas.py` (PySpark `StructType` schemas for the activity log, the chunk, and the chunked document).

### Databricks helpers (`dbxhelpers/`)

Configuration lives in `config/`: `common_config.yaml` (the embedding endpoint `databricks-gte-large-en`, top_k of 5, LLM endpoints defaulting to gpt-4o-mini, temperature 0.0, max_tokens 1000, request_timeout 20, MLflow experiment paths, the app name `gkpolicychatbot-ui`, and evaluation settings of 40 questions over 20 sampled documents), `env_config.yaml` (per-environment catalog, schema, volume, secret scope, index endpoint and name, embedding source column, workspace URL, serving workload type and size, SharePoint folder id, and service-principal secret keys), `jobs_config.py` (the `Config` class merging common and environment settings into attributes via `_dict_into_attr()`), and `config_helpers.py`.

`database.py` provides `get_dbutils()`, `check_if_table_exists()`, `write_to_db()`, `merge_to_db()`, `combine_dataframes()`, `get_table_or_empty()`, `create_sha_key()`, and `check_column_exists()`. `databricks_serving.py` manages endpoints with `get_served_entity_specs()`, `update_endpoint_config()` (pruning old model versions beyond a default of ten, max fourteen), `create_new_config()` (with scale-to-zero based on traffic), and `trigger_endpoint()` (start/stop via the serving API). `mlflow.py` provides `get_or_create_experiment()`, `create_or_replace_dataset()`, `get_mlflow_run_by_model_tag()`, `get_model_version_by_alias()` (champion or challenger), `get_served_versions_as_int()`, and `get_versions_to_delete()`. `agent_evaluation_utils.py` plots scorer comparisons, evaluation results, and latency, and wraps the MLflow generic scorers (Correctness, Guidelines, RelevanceToQuery, RetrievalGroundedness, RetrievalRelevance, RetrievalSufficiency, Safety).

### Pipeline jobs and orchestration

The pipeline is defined in `databricks_resources/databricks_workflows.yaml` as five jobs. Job one, `sync_sharepoint_to_blob_to_index` (scheduled daily at 12:00 UTC), runs `set_up_sync_mode` (incremental versus full refresh), index- and GPT-endpoint setup, `sharepoint_to_blob_sync` (producing `br_sync_log`), `snapshot_blob_storage` (producing `br_sync_blob_policies_snapshot`), `bronze_chunks` (extracting text and chunking semantically, producing `br_chunks` and `br_chunk_log` and an `update_index` flag), a conditional gate, `refresh_silver_chunks` (deduplicating and validating into `sr_chunks` with a `dq_quarantined_chunks` quarantine table), and `sync_indexer` (creating or syncing the Delta Sync index). Job two, `agent_register_challenger`, logs the model to MLflow, runs a predeployment check, registers the challenger version, and evaluates it against the generated dataset. Job three, `agent_deploy_champion`, deploys the champion to the serving endpoint, marks the champion alias, and creates the AI App if absent. Jobs four and five, `services_on` and `services_off`, start and stop the endpoint and app (the latter scheduled nightly to save cost).

### Tables and the vector index

The bronze layer holds `br_sync_log`, `br_chunks`, `br_chunk_log`, and `br_sync_blob_policies_snapshot`. The silver layer holds `sr_chunks` (deduplicated, quality-checked, with columns id as primary key, content, chunk_title, file_name, url, document_title, file_id, and index_content for embedding) and `dq_quarantined_chunks`. The vector index is `{catalog}.{schema}.gkpolicychatbot_index_v2` on endpoint `gkpolicychatbot_endpoint`, using the `databricks-gte-large-en` embedding model in triggered (manual) sync mode.

### RAG specifics

Documents are ingested from SharePoint via Graph API, tracked through state snapshots for incremental syncing, and downloaded to blob. Text extraction uses pypdf for PDFs and python-docx for DOCX, with magic-byte format detection. Chunking is LLM-driven (gpt-4o-mini via ChatDatabricks), targeting 500–1000 words and respecting natural boundaries, emitting per-chunk title, questions, word count, and ordinal number, plus a document title and summary. Embeddings use `databricks-gte-large-en` applied to the index_content column, synced via triggered refresh. Retrieval performs similarity search returning the top five chunks with metadata and relevance scores, grades them with an LLM, and passes survivors to generation. Generation receives context as a JSON array of sources and enforces the `<cite N>` citation format mapped to `Reference` objects, with `remove_cite_tags` stripping the markers before display.

### Deployment, CICD, and config

The Azure DevOps pipeline (`azure_pipeline/cicd.yaml` with `test_and_build_template.yaml` and `deployment_template.yaml`) handles build (Hatch-based tests, pytest with coverage, Ruff linting, `databricks bundle validate`) and release (`databricks bundle deploy`), with environment detected from branch (development to dev, test to test, main to prod) and secrets injected from Azure Key Vault. The Databricks Asset Bundle is named `gkpolicychatbot`, with dev, test, and prod targets bound to their git branches, workspace roots, and schedules. Runtime environment variables include the Databricks host and service-principal client id and secret; Databricks secrets (scoped per environment, for example `z106ddatabrickskvgenai`) include the Databricks and sync service-principal credentials, the Azure OpenAI key and URL, and the tenant id. The runtime `AgentConfigSchema` carries the LLM endpoint dictionary, top_k of 5, the index endpoint and name, the catalog and schema, temperature 0.0, max_tokens 1000, and a 20-second timeout.

### Input and output formats

The agent input (`ResponsesAgentRequest`) carries an input message list, optional context (user, conversation, and session identifiers), and custom inputs. The output (`ResponsesAgentResponse`) carries text outputs plus custom outputs including the trace id, the rephrased question, and the list of retrieved sources. Each source carries chunk id, content, chunk title, file name, document URI, document title, and score. The answer JSON carries the answer text with embedded `<cite N>` markers and a references array of citation number, chunk title, and document title.

### Evaluation

The evaluation dataset is forty auto-generated questions drawn from twenty sampled documents, produced with the mission statement and `evaluation_questions_guidelines` to mimic realistic pub-manager and kitchen-manager queries. LLM evaluators from `mlflow.genai.scorers` cover Correctness, RelevanceToQuery, RetrievalGroundedness, RetrievalRelevance, RetrievalSufficiency, Guidelines (UK English, professional tone), and Safety. The flow generates or retrieves the dataset, runs the agent over each question, collects predictions and sources, scores with the evaluators, compares challenger against champion, and logs to MLflow, with models registered in Unity Catalog and aliased champion or challenger for safe promotion.

### Notable implementation details

Incremental sync uses blob-stored state snapshots to detect only new, modified, or deleted files. Document grading runs in parallel threads preserving telemetry context. Both intent and answer use Pydantic structured outputs for deterministic parsing. Semantic chunking preserves meaning better than naive token splitting and yields searchable per-chunk questions. MLflow traces every step with user and session context. Citation enforcement is validated against the source list. Environment separation is YAML-driven. Model versioning uses the challenger-champion workflow with automatic evaluation. Services auto-stop nightly in dev and test to reduce cost. A quarantine table isolates chunks failing validation for selective reprocessing.
