# FSA — Field Service Agent (Databricks Backend and UI)

## Part One — Business Overview (for all readers)

The Field Service Agent (FSA) answers questions about water-treatment equipment from a library of technical documents. The engineers and operators who use it work in the field. They maintain pumps, valves and treatment plant, they follow written procedures, and they check engineering drawings, maintenance records, asset specifications and regulatory documents. That knowledge sits in thousands of PDFs and Word files. Searching it takes time, and reading it takes longer while you are standing in front of the equipment.

You ask in plain language: the maintenance procedure for a specific asset, or the content of a drawing. FSA replies with an answer and the documents it came from. It reads the images, diagrams and tables inside a document as well as the text, and it accepts a photo from you, of a piece of equipment or a nameplate, as part of the question. Every answer carries its sources, images included, so you can check any claim against the page it came from.

Field staff stop hunting through document libraries. The library follows the ISO 19650 naming standard, and the pipeline re-indexes documents as they arrive or change, so an answer reflects the current revision rather than a superseded one.

Two projects make one system. The backend, fsa-databricks, processes the documents, runs the reasoning and serves the model. The frontend, fsa-databricks-ui, is the web application people work in. Both run on Databricks.

## Part Two — How It Works End to End (for semi-technical readers)

FSA has two halves: a pipeline that prepares documents for search, and an agent that answers questions. Both run on Databricks, and people reach them through the web app.

The **document pipeline** turns raw files into searchable knowledge. Someone drops documents into a cloud storage folder, and the pipeline scans it and picks a mode: process everything, process the new and changed files, or process a ten-file sample for testing. It converts Word files to PDF and pulls out the text and the images. A vision model then reads the engineering drawings, describes each image and turns tables into structured data. A second model splits the text into chunks and gives each chunk a title, a category, a summary and the questions it can answer. The pipeline embeds every chunk and loads it into two indexes, one that searches by meaning and one that matches exact terms. It records the state of every file at every stage, clears out deleted documents, and logs whether a run succeeded, which tells the next run whether to sync in full or sync the difference.

The **agent** answers the questions as a graph of steps. It decides first whether a message is chit-chat or a question. For a question, it rewrites the text so it stands without the conversation around it, then extracts the assets you named and picks one of seven document categories, both at once. It retrieves the closest chunks. When you attach a photo, it embeds the photo, a description of the photo and your text, then averages the three into one query. A grader scores each chunk against a five-point rubric and penalises chunks about the wrong asset. The grader sees the images too, so it judges a drawing instead of guessing at it. When strong enough sources survive that grading, the agent writes the answer and embeds the source images in its reasoning.

We package the agent as a model on a serving endpoint that scales to zero when nobody is using it. The interface takes typed questions, spoken ones transcribed as you talk, and uploaded images. Databricks Asset Bundles carry the deployment and the configuration, and we trace every invocation, so an engineer can open any answer and follow the path the agent took to it.

## Part Three — Deep Technical Reference (for engineers)

### Domain and structure

FSA is a retrieval-augmented generation chatbot on Databricks for water-treatment field-service operations, spanning engineering drawings, procedures, maintenance records, asset specifications, and regulatory documents organised loosely under ISO 19650 naming. It comprises the backend `fsa-databricks` (pipelines, LangGraph agent, FastAPI API, MLflow serving), the frontend `fsa-databricks-ui` (a Next.js React app plus a lightweight FastAPI proxy), and a deployment layer of Databricks Apps, Asset Bundles, and Unity Catalog. The data architecture follows a medallion pattern: source Volume to bronze tables to a silver table to two search indexes.

### The three Databricks workflows

The **ingestion pipeline** (`fsa_ingestion_pipeline`, scheduled at 02:00 UTC but paused, single concurrent run, twelve-hour timeout) runs on a classic eight-worker cluster plus serverless, across roughly eleven tasks. `cluster_warmup` pre-warms the cluster. `scan_and_setup` (`ScanAndSetupJob`, serverless) walks the `fsa_documents_dev` Volume, detects sync mode (full, incremental, or sample of ten), performs ISO 19650 revision deduplication (marking older revisions SUPERSEDED), and populates the `files_to_process` queue and `file_tracking` registry, recording the run in `sync_state`. Conditional gates check whether processing or deletion is needed. `convert_docx_to_pdf` converts Word files via headless LibreOffice with four worker threads and a two-minute per-file timeout. `delete_documents` (a child deletion pipeline) runs in parallel when deletions are detected. `extract_text` (`ExtractTextJob`) opens PDFs with PyMuPDF, excludes files over 10 MB (EXCLUDED) or over 20 pages (SKIPPED), writes a raw-text placeholder row per document and one drawing-page row per page of engineering drawings, into `chunks_bronze_text` and `chunks_bronze_images`. `extract_metadata` (`ExtractMetadataJob`) performs three-pass title extraction (regex, then a vision LLM on the first-page image, then filename fallback), determines doc type, number, revision, three document dates, and an assets JSON, rate-limited to sixty requests per minute with ten concurrent and a 120-second timeout, and reclassifies misidentified drawings. `analyze_images` (`AnalyzeImagesJob`) uses a vision LLM to describe images and tables, filtering at a 0.7 minimum confidence, writing image and table rows with base64 image data, analysis text, and CSV table data in batches of 500. `llm_chunk` (`LlmChunkJob`) performs LLM semantic chunking with Azure OpenAI gpt-4.1-mini, producing per chunk a content body, title, one of seven document categories, summary, page number, and five hypothetical questions, falling back to size-based chunking (1000 characters, 200 overlap) on failure, and deleting placeholder rows on success. `generate_text_embeddings` (`GenerateTextEmbeddingsJob`, serverless) embeds text chunks with Cohere embed-v-4-0 (1536 dimensions, batches of 96), appending the chunk's questions to the text before embedding. `generate_image_embeddings` (`GenerateImageEmbeddingsJob`, serverless) embeds image descriptions and table CSVs (batches of 100, with a keepalive thread). `update_vector_search` (`UpdateVectorSearchJob`) maintains the Delta Sync index with three imputation passes for missing category, dates, and assets, choosing trigger-only sync for matching incremental runs or a full delete-and-recreate for full runs or column changes, and writing the critical SUCCESS row to `sync_history`. `update_bm25` (`UpdateBm25Job`) maintains a pickled keyword index in the `fsa_indexes_dev` Volume, rebuilding from scratch in full mode or appending and deduplicating in incremental mode, using Reciprocal Rank Fusion for hybrid merging.

The **deletion pipeline** (`fsa_deletion_pipeline`, serverless, thirty-minute timeout) runs a single `DeleteDocumentsJob` in auto, manual, or delete-all modes. It connects to Vector Search, queries bronze for chunk IDs belonging to target paths and deletes them from `chunks_silver` (the source of truth), triggers a Vector Search sync, rebuilds BM25 from scratch (the pickle has no remove operation) keeping only non-deleted chunks marked SYNC_TRIGGERED, hard-deletes bronze rows and soft-deletes registry rows, and writes a full `deletion_log` audit row. Partial deletions do not fail the job, so success must be verified against `deletion_log`.

The **agent deployment pipeline** (`fsa_agent_deployment`, serverless, three sequential tasks) runs `agent_log_model` (registering the MLflow model `field_service_agent`, bundling the agent script and wheel, and freezing configuration: gpt-4.1-mini at API version 2024-12-01-preview, Cohere embed-v-4-0 at 1536 dimensions, vector_only retrieval mode, grading enabled with a 0.2 score threshold and 0.8/0.2 LLM-to-distance weighting), `agent_deploy_endpoint` (deploying to `field-service-agent-endpoint` as CPU, Small, scale-to-zero, polling to readiness), and `agent_deploy_ui` (deploying the FastAPI app as the Databricks App `fsa-ui` pointed at the endpoint).

### Delta tables

All tables sit in `facatalog.fsa_schema`. Run bookkeeping comprises `sync_state` (run startup, always INITIATED), `sync_history` (the critical success record — absence of SUCCESS rows forces the next run to full mode), and `files_to_delete` (the hand-off to the deletion pipeline). File-level tracking comprises `files_to_process` (keyed on run id and file path, carrying per-stage status columns for extraction, metadata, analysis, chunking, text and image embedding, and overall processing, with a retry predicate picking up NULL, FAILED, or IN_PROGRESS rows) and `file_tracking` (keyed on file path, carrying processing status of PENDING, COMPLETED, EXCLUDED, SUPERSEDED, DELETED, or FAILED, an is_deleted flag, timestamps, and document identity). Chunk tables flow bronze to silver to indexes: `chunks_bronze_text` (raw_text placeholders becoming text chunks), `chunks_bronze_images` (drawing_page, image, and table rows, kept separate from text to avoid concurrent-append conflicts), and `chunks_silver` (the authoritative embedded table carrying the 1536-float embedding, mirrored by the Vector Search Delta Sync index). Index and audit tables comprise `vs_metadata`, `bm25_index_history`, and `deletion_log`. Non-table artifacts are the Vector Search index `facatalog.fsa_schema.fsa_chunks_index` on endpoint `fsa-vs-endpoint`, the `bm25_index.pkl` BM25 pickle in `fsa_indexes_dev`, and the source `fsa_documents_dev` Volume.

### Parameters

Environment bindings (`jobs/config/config_files/env_config.yaml`) set the catalog `facatalog`, schema `fsa_schema`, secret scope `fsa_secrets_dev`, the documents and indexes Volumes, and SQL warehouse `73dde9a41e3132e9`. Ray uses eight workers with 4 GB object store each on a Spark 18.1.x-cpu-ml classic cluster of Standard_DS3_v2 nodes. Ingestion parameters include a sample size of ten, the 10 MB and 20-page exclusion limits, four conversion workers at 120 seconds each, metadata extraction at batch 25 and 60 requests per minute with semaphore 10 and three retries, image analysis at 0.7 confidence, 60 requests per minute, 300-second timeout, 4000 max tokens, and 500-row write batches, LLM chunking at strategy "llm", 60 requests per minute, semaphore 10, 100k-token windows, five questions, and 1000/200 fallback sizing, text embedding batch 96, image embedding batch 100, and vector-search columns whose editing forces an index rebuild. Agent and grading parameters (frozen into the model) include gpt-4.1-mini, Cohere embed-v-4-0, vector_only retrieval, grading at temperature 0.0, max_tokens 300, max context 7500 tokens, score threshold 0.2, and final-score weighting of 0.8 LLM to 0.2 distance.

### ISO 19650 and document identity

The standard format is project, originator, volume, location, number, and description. Implementation in `processing/document_metadata.py` parses discipline-coded document numbers (such as DWG-CST-G01-001), parses revisions from `_Rev`, `-Rev`, `_R`, and `_P` patterns, deduplicates revisions by marking lower revisions SUPERSEDED, and classifies doc type from filename markers (`-DWG-`, `-DOC-EII-` for electrical, `-DOC-CST-` for civil mapping to drawings).

### LLM chunking and parallelization

Implemented in `processing/llm_chunking.py`, the approach is asyncio plus a sliding-window deque RateLimiter plus a Semaphore for in-flight concurrency, chosen because the bottleneck is Azure OpenAI latency rather than CPU (a Pandas UDF would add serialization overhead without benefit). All documents are collected on the driver and processed concurrently via `chunk_text_llm_batch()`, `extract_async()`, `extract_from_window_async()`, and `merge_summaries_async()` over a shared aiohttp session, tuned by requests-per-minute and semaphore limits, producing the per-chunk content, title, category, summary, page number, and five hypothetical questions appended before embedding.

### The LangGraph agent

The agent uses LangGraph with no tool-calling — all capabilities are deterministic graph nodes. Its state (`agent/models.py`) carries messages, the rephrased question, intent, document retrieval category, asset properties, sources, an optional query image and its analysis, the first source image for display, and an optional site filter. The graph (`agent/graph/agent_graph.py`) routes from START through `detect_intent` to either a social reply and END, or to `rephrase_question`, then either to `no_question` and END or to a fan-out gateway running `extract_asset_properties` and `detect_document_retrieval_category` in parallel, converging at `route_retrieval`, which dispatches to either the multimodal retriever (when an image is present) or the text retriever, both feeding `grade_documents`, which decides between the generator (when the maximum score reaches 0.2) and `no_answer`.

`detect_intent` classifies social versus question at temperature 0.0. `rephrase_question` rewrites the message as a standalone question from the last three turns, returning the literal "no_question" when no information-seeking intent exists. `extract_asset_properties` extracts a structured asset list (name, identifier, and aspects among dimensions, operations, maintenance, installation, and inspection) via a Pydantic `AssetPropertiesList`, fault-tolerantly continuing on failure. `detect_document_retrieval_category` routes to one of seven categories (Incident/Issues, Maintenance/Field work, Procedures/Instructions, Engineering/Design, Asset Replacement/Renewal, Reports/Assessments, Regulatory/Compliance) with three retries. `retriever` performs text retrieval, in production via a single vector search with site, category-plus-Other, and ITR-exclusion filters, top-k five (the agent constructor can override to three), enriching results with base64 image data fetched from `chunks_silver` via the SQL warehouse since the index omits images. `multimodal_retriever` handles photo questions by computing three Cohere embeddings (the image, its description, and the question text) and fusing them by element-wise averaging into one query vector, gracefully degrading to text retrieval on any failure. `grade_documents` applies a five-criterion rubric (directness, completeness, specificity, accuracy, clarity, each scored 0–2 for a total 0–10) per chunk in parallel threads at temperature 0.0 in JSON mode, injecting an asset-focus instruction to penalize off-asset chunks, attaching low-resolution images for visual chunks, and blending the LLM rubric score with the vector similarity score at 0.8 to 0.2, never dropping a chunk and falling back to a neutral 0.5 on grading failure. `generator` assembles a multimodal prompt of system message, question, each source as a JSON block, and the actual low-resolution source images, at temperature 0.2 with an `Answer` structured output, setting the first source image for the UI. `social` replies warmly at temperature 0.7 with a hardcoded fallback, and `no_question` and `no_answer` return clear inability messages. Prompts live in `agent/prompts/` across intent, document retrieval category, asset properties, grading, generation, and social modules.

### Retrieval internals

The `DocumentRetriever` (`retrieval/retriever.py`) lazily initializes the Vector Search client and index, supports `use_hybrid` and a vector weight, and dispatches `retrieve(query, k, site, doc_category)` to vector or hybrid paths. Vector search queries `fsa_chunks_index` with a Cohere-embedded 1536-dimension query under site, category-plus-Other, and ITR-exclusion filters. The disabled hybrid path retrieves 2000 from vector and BM25 (and optionally PageIndex), merges by Reciprocal Rank Fusion (weight divided by sixty plus rank), and preserves per-engine scores. Image enrichment fetches base64 image data from `chunks_silver` via the SQL Statement Execution API with external links, polling up to two minutes for warehouse cold-start. The `CohereEmbedder` (`retrieval/embeddings.py`) wraps embed-v-4-0 at 1536 dimensions via the azure-ai-inference SDK.

### Backend web API

The FastAPI app (`web/app.py`) exposes chat (`POST /api/chat`), full session management (list, create, get, rename, delete, history), a legacy search endpoint, the HTML chat page, a mounted PDF.js viewer, and static UI assets. It handles multimodal input (text, audio transcribed by AssemblyAI over WebSocket streaming, and base64 images pre-analyzed before reaching the agent), site isolation, session persistence keyed on thread id, MLflow tracing of every invocation, and database-fetched image serving to avoid response bloat. API models (`web/api/models.py`) define `ChatMessageRequest`, `ChatMessageResponse`, `SourceInfo`, the session request and response types, and `ConversationHistory`.

### Frontend

The frontend serving layer (`fsa-databricks-ui/web/app.py`) is a FastAPI app serving the static Next.js export from `ui/apps/web/out/`, proxying `/api/*` to the backend serving endpoint with Databricks App machine-to-machine OAuth, and streaming ONNX Runtime WASM and MJS assets from the `fsa_static_assets_dev` Volume, allowing localhost CORS in local mode. The build is Next.js 14.2.29 on React 18.3.1 in a pnpm monorepo with Tailwind CSS, workspace packages `@fsa/core` and `@fsa/ui-tokens`, lucide-react icons, and a pre-built static export. Hooks include `useAssemblyAIStreaming.ts` for audio and `useChatAPI.ts` for chat. The proxy extracts Databricks App identity headers (`X-Forwarded-Email`, `X-Forwarded-User`) and streams ONNX assets from the Volume with browser caching.

### Models, credentials, and providers

The LLM is Azure OpenAI gpt-4.1-mini (API version 2024-12-01-preview) used for metadata extraction, image and table analysis, chunking, grading, generation, and intent/rephrase/category detection, via the azure-ai-inference, openai, and langchain-openai SDKs. The embedding model is Cohere embed-v-4-0 at 1536 dimensions for text chunks (batch 96), image and table descriptions (batch 100), and query embedding. Vision analysis reuses gpt-4.1-mini for first-page title crops, per-image scoring, and query-image analysis. Speech-to-text uses AssemblyAI via WebSocket streaming. All LLM operations share a 60-requests-per-minute, ten-concurrent rate envelope. Secrets live in the `fsa_secrets_dev` scope (LLM endpoint and key, embedding endpoint and key, and the AssemblyAI key).

### Infrastructure and deployment

The Databricks Asset Bundle is named `field_service_agent`, with a workspace root under `/Workspace/bundles/fsa/${bundle.target}`, including variables, workflows, and apps, syncing the app, agent, retrieval, shared, and web code while excluding caches and node modules, and building a wheel artifact via `scripts/databricks_package_build.sh`. Targets include dev, test, test-domenico, and nwl-dev (production mode, develop branch, with named CAN_MANAGE permissions). The backend app.yaml runs uvicorn against `web.app:app` on port 8000 with the serving endpoint name, catalog, schema, documents Volume, SQL warehouse, and all API secrets; the frontend app.yaml sets the deployment environment, build directory, backend URL, and Volume references and links the backend app via OAuth. Unity Catalog provides the catalog `facatalog`, schema `fsa_schema`, the three Volumes (`fsa_documents_dev`, `fsa_indexes_dev`, `fsa_static_assets_dev`), the serverless Vector Search endpoint `fsa-vs-endpoint`, and the serving endpoint `field-service-agent-endpoint` (CPU, Small, scale-to-zero, cold-start one to two minutes).

### End-to-end message flow

A user query (text, audio, or image) reaches the Next.js UI, which calls `/api/chat` proxied through the UI app to the backend FastAPI, which transcribes audio, pre-analyzes any image, creates or reuses a session, and forwards to the serving endpoint. The endpoint loads the MLflow-packaged `FieldServiceAgent` and invokes `chat()`, which seeds state and runs the LangGraph graph through intent detection, rephrasing, parallel asset and category extraction, retrieval or multimodal retrieval, parallel grading, the generate-or-decline decision, and generation. The agent formats the answer, sources with metadata, and first source image, and the backend returns JSON that the frontend renders as cited answer text, source cards, and inline images, supporting multi-turn conversation via the thread id.

### Documentation and known gaps

A handover documentation set lives under `docs/handover/pipelines/` numbered 00 through 07 (overview, sync modes, ingestion pipeline, deletion pipeline, agent deployment pipeline, tables and status model, parameters reference, and the LangGraph agent). Known production considerations include that conversation memory uses an in-process MemorySaver that does not survive scale-to-zero restarts (a SQLiteSaver on a Volume would fix this); the hybrid BM25 and PageIndex retrieval is complete but disabled in favour of vector-only; the hybrid BM25 mode loses the category filter; some docstrings carry stale 0.6/0.4 weighting and 1024-dimension references (the real values are 0.8/0.2 and 1536); the site parameter is undeclared in the state TypedDict though it works; image data is fetched at chat time without caching, adding latency on warehouse cold-start; and a BM25 deletion edge case can silently drop chunks completed but never published, mitigated by the SYNC_TRIGGERED filter.
